GitHub Actions
В проекта е конфигуриран GitHub Actions workflow файл `ci.yml`, който се намира в директорията `.github/workflows` (редове 1-33 в `.github/workflows/ci.yml`). Workflow-ът се изпълнява автоматично при всеки `push` и `pull_request` към `main` branch-a (редове 3-10). Дефиниран е един job с име `build-and-test`, който се изпълнява на `ubuntu-latest` (редове 12-15). Първо се клонира репото с `actions/checkout@v4` (редове 18-20), след това се инсталира Node.js версия 22 с `actions/setup-node@v4` и се активира npm cache (редове 22-27). След това се изпълнява `npm ci` за инсталиране на зависимостите (редове 29-30). При успешна инсталация се изпълняват последователно стъпките за linter, компилиране и unit тестове – съответно `npm run lint`, `npm run build` и `npm run test:cov` (редове 32-39). При успех GitHub Actions показва зелена отметка за job-a и за целия workflow, а при проблем job-ът спира на съответната стъпка и се отбелязва с червен X.

Pipeline Tests
Unit тестовете са конфигурирани с Jest чрез настройките в `package.json` (редове 95-111). Root директорията за тестовете е `src`, а всички файлове, завършващи на `.spec.ts`, се третират като unit тестове (редове 101-102). Тестовете се стартират в pipeline-a чрез стъпката `Test with coverage`, която извиква командата `npm run test:cov` (редове 37-39 в `.github/workflows/ci.yml`). Скриптът `test:cov` е дефиниран в секцията `scripts` на `package.json` и изпълнява `jest --coverage` (ред 18 в `package.json`), което генерира отчет за покритието в директорията `coverage` (ред 109). Пример за модулни тестове са файлът `src/books/books.service.spec.ts`, който тества логиката на `BooksService` (редове 1-190), и файлът `src/app.controller.spec.ts`, който тества основния контролер на приложението. В pipeline-a тестовете се изпълняват след успешния lint и build, така че ако някой тест пропадне, целият job се маркира като неуспешен.

Pipeline Linter
Linter-ът е конфигуриран с ESLint чрез файла `eslint.config.mjs`, който се намира в root директорията (редове 1-34 в `eslint.config.mjs`). Използвана е базовата конфигурация `@eslint/js`, TypeScript конфигурациите от `typescript-eslint` и препоръчителната конфигурация за `eslint-plugin-prettier` (редове 2-5 и 11-13). За да се настрои към кода на проекта, са дефинирани глобални променливи за Node и Jest (редове 15-19), а `sourceType` е зададен на `commonjs` (ред 20). Допълнително са изключени някои по-строги TypeScript правила, като `@typescript-eslint/no-explicit-any` (ред 29), а други са понижени до предупреждения, например `@typescript-eslint/no-floating-promises` и `@typescript-eslint/no-unsafe-argument` (редове 30-31), за да могат да се използват по-гъвкави конструкции в съществуващия код. В `package.json` е дефиниран скриптът `lint`, който изпълнява `eslint "{src,apps,libs,test}/**/*.ts" --fix` (ред 15 в `package.json`). В pipeline-a linter-ът се стартира в стъпката `Lint` на workflow файла (редове 32-33 в `.github/workflows/ci.yml`). При грешки в linter-a job-ът се маркира като неуспешен, а конкретните проблеми се виждат в логовете на GitHub Actions.
